# claude-usage: cross-machine sync + dashboard

A living spec for the part of `claude-usage` that pushes per-message token/cost aggregates from local Claude Code transcripts to a hosted MongoDB collection, and renders them on a small Next.js dashboard. Written for someone who has never seen this codebase and needs to modify it safely.

The local-only half (status line, on-demand report) predates this feature and isn't covered here except where it shares code with sync.

## What the system does, end to end

Claude Code writes one JSONL transcript per session under `~/.claude/projects/<project-dir>/`, plus nested transcripts for subagents. Two hooks and one CLI turn that into hosted rows:

- **`hooks/user-prompt-submit.mjs`** fires on every prompt. It spawns `bin/sync.mjs` as a detached, `stdio: "ignore"` child and exits immediately — the upload never adds latency to a prompt.
- **`hooks/session-start.mjs`** fires on session boundaries (startup, resume, clear, compact, fork). It `await`s `bin/sync.mjs` inline, so a session opens already caught up.
- **`bin/backfill.mjs`** is a manual, re-runnable command that walks the whole `~/.claude/projects` tree once (main sessions + every nested subagent transcript) — the one-time catch-up for history that predates sync being turned on.

Inside `bin/sync.mjs`, the pipeline is the same regardless of caller:

1. Read raw JSONL records — `src/parser/read.mjs`'s `readTailRecords` (last 256 KiB, the cheap per-prompt path) or `streamRecords` (whole file, fixed 1 MiB chunks, bounded memory — the sweep path used by `SessionStart` and backfill).
2. `src/parser/dedupe.mjs` collapses Claude Code's repeated streaming copies of each assistant message into one `Turn` per `(requestId, messageId)`.
3. `src/parser/project.mjs` / `src/parser/repo.mjs` resolve project and repo identity once per project directory (memoized, not per turn).
4. `src/parser/events.mjs`'s `mapTurnToEvent` turns a `Turn` into a `MappedUsageEvent` — the aggregates-only shape that is the only thing ever serialized into a request body.
5. `bin/sync.mjs`'s `postEvents` batches (2,000 events/request — Vercel's request body cap is a hard 4.5 MB) and `POST`s to `/api/sync` with a shared secret in `x-claude-usage-secret`.
6. `src/app/api/sync/route.ts` validates the batch and calls `src/server/usage-store.ts`'s `saveUsageEvents`, which upserts into the `usage_events` MongoDB collection.
7. `src/app/page.tsx` and `src/app/session/[id]/page.tsx` query `src/server/usage-queries.ts` (cost per day by machine/project/model, cache/subagent efficiency, per-session model breakdown) and render charts and tables, gated behind a shared-secret login (`src/proxy.ts`).

## Invariants

These are load-bearing — each was expensive to establish (a real defect or a proven attack), and undoing any of them silently reintroduces what it was built to prevent.

- **Aggregates, plus the session title — and nothing else — leave the machine.** This used to read "transcript content never leaves the machine", and that is no longer true: `sessionTitle` (Claude Code's own `ai-title` record) is model-generated *from the conversation*, and is uploaded deliberately so the dashboard's session list is distinguishable — rows otherwise repeat the same project and machine with the id only in a link target. It is the single exception, admitted with the tradeoff understood: a title can name a client, an incident or a repo, and it lands in Atlas. `lastPrompt` sits in the same transcripts, is raw prompt text, and must **never** join it. Both allowlists below name `sessionTitle` explicitly so the exception stays a decision rather than an accident. Two independent allowlists enforce this at different points — the mapper (`src/parser/events.mjs`'s `mapTurnToEvent`, which builds `MappedUsageEvent` as an explicit object literal, never a spread of the raw record) and the server (`src/app/api/sync/route.ts`'s `REQUIRED_STRING_FIELDS`/`OPTIONAL_STRING_FIELDS`/etc., which also builds a fresh object literal). The server-side allowlist exists in its own right, not just as a mirror of the client's: an adversarial review (`ADVERSARIAL_REVALIDATION.md` R7) proved that trusting the client-side allowlist alone would let a field like `promptText` reach Mongo if a client ever skipped the mapper — the server allowlist is what actually stops that, independent of what the client sends. Per-event *type* validation (`isValidUsageEvent`, checking `typeof` on every allowlisted field) is a second, distinct layer on top of the key allowlist: the same review proved that a key-only allowlist still lets a value of the wrong shape through, and an operator-injection probe sent `requestId: {"$gt": ""}` as a "string" field — because the identity fields flow straight into `usage-store.ts`'s `updateOne` **filter**, that operator value matched an arbitrary pre-existing document and silently rewrote it (cost inflated, account reattributed, no error, no trace). The type check closes that: `typeof event.requestId !== "string"` now rejects the event before it ever reaches the filter.

- **Dedupe on `(requestId, messageId)`, taking MAX output tokens.** Claude Code writes repeated streaming copies of each assistant message as it's generated; an early copy holds a partial token count (`src/parser/dedupe.mjs` measured this at ~38% undercount if the first copy were kept instead of the last/highest). `dedupeAssistantTurns` keeps whichever copy has the highest `output_tokens`. The same `(requestId, messageId)` pair is also the collection's unique index (`usage-store.ts`'s `message_identity` index) — this is what makes re-sending an already-synced range free and is why overlapping syncs from two machines (or a tail sync racing a full sweep) collapse instead of double-counting.

- **The upsert splits by field role.** `saveUsageEvents` (`src/server/usage-store.ts`) does not `$set` the whole document:
  - **Ownership fields** (`sessionId`, `machineId`, `model`, `timestamp`, `isSubagent`) use `$setOnInsert` — written once, on first insert, never again. This protects against a forked session's re-sync re-stamping `sessionId` on an inherited message and migrating its cost out of the parent session's drill-down (a session can never exist on two machines, so first-writer-wins is well-defined — D18).
  - **Attribution fields** (`projectSlug`, `repoKey`) were in that group and have been **moved to `$set`** — see the reversal below. `repoKey` is spread in only when resolved, so a sync that could not resolve one never blanks an answer a better-placed sync already gave.
  - **Counts and cost** (`inputTokens`, `cacheReadTokens`, `cacheWrite5mTokens`, `cacheWrite1hTokens`, `outputTokens`, `costUsd`) use `$max` — a sync that caught a message mid-stream carries partial counts, and `$max` makes it impossible for a later, more-complete sync to be overwritten by an earlier, partial one. Cost rises monotonically with output tokens for the same message, so it is safe to `$max` too.
  - **Everything else** (`priced`, and `accountUuid`/`orgUuid` when known) uses plain `$set` — always the mapper's latest determination. `priced` is deliberately never `$max`'d: BSON orders `false < true`, so a `$max` on a boolean can only ratchet toward `true` and could never let a corrected re-sync demote a wrongly-`true` value back down.
  - **Reversal — attribution is now last-writer-wins.** `projectSlug`/`repoKey` were originally `$setOnInsert` on the reasoning that they identify *which repository a message belongs to*, an ownership fact, so D18's first-writer-wins rule applied to them exactly as to `sessionId`. That held while attribution was resolved once per project **directory**, where a later sync could only be a *different* guess, never a better one.

    Per-turn attribution broke that premise: a resync is now strictly better informed. Under the old rule a re-backfill could not have corrected a single one of the 55,158 already-stored events — every one would have kept its "no repository" answer permanently, and the only recovery would have been dropping the collection. Correcting history is the entire point of the feature, so these two fields moved to `$set`.

    D18's actual concern is untouched: `sessionId` remains `$setOnInsert`, so a forked session still cannot migrate an inherited message out of its parent's drill-down.

- **Cost is frozen at write time, priced from the message's own timestamp.** `src/parser/pricing.mjs`'s price table is effective-dated (`{ from, input, output }` periods per model, oldest first) specifically because Sonnet 5's introductory rate (`$2`/`$10` per million input/output) expires 2026-09-01 and reverts to list (`$3`/`$15`). A flat, non-dated table would silently reprice every already-stored historical event the moment the rate changes; effective-dating means a turn from before the cutover keeps the price it was actually billed at, forever, regardless of when the dashboard queries it.

- **`priced` means "this cost is trustworthy", not "the model name is known".** `isPricedModel(model) && Boolean(turn.timestamp)` — false whenever `costUsd` cannot be trusted, which is two distinct cases folded into one flag: an unpriced/unknown model (which prices at `$0`, indistinguishable from genuinely free work without this flag), or a missing timestamp (`priceAt` needs one to pick the right effective-dated period). Every dashboard total that sums `costUsd` filters or annotates on this flag rather than trusting the raw number.

- **Attribution is resolved per TURN; the project directory is only the fallback.** `attributeTurns` (`src/parser/attribution.mjs`) places each turn on its own evidence, in falling order of directness: the directory the turn actually ran in, else the repository holding most of the files that turn read or wrote, else the repository the session is already in, else the project directory's own identity. Ties among files break toward the repository already in play, then toward whichever was touched first, so the same turn always attributes the same way.

  `cwd` deliberately outranks the files: a turn running inside one repository while *reading* a file from another is working on the first. Where `cwd` is a parent folder it resolves to nothing and the files decide — which is the entire case this exists for. A session launched from a directory that *contains* repositories rather than being one previously attributed 100% of its spend to that parent. Predicted at **93.1%** by a dry run over the local transcripts, then confirmed in production after the corrective backfill: repo-less spend fell from **54.8% to 7.8%** of all spend, `repoKey` coverage went 25,013 → 60,647 events, and distinct project slugs went 7 → 68.

The single figure that validated the whole change was `personal/quant-trading` landing at **$1,766.90 / 14,642 events** against a pre-build prediction of ~$1,750 — parser and store agreeing on a number neither could fake.

  The per-turn resolver (`resolveRepoAt`) caches misses as well as hits, unlike the per-directory ones below: it resolves a real filesystem path, which will not become a repository mid-run, and the misses are both the common case and the expensive one to re-ask.

- **Project identity is the last two path segments of a directory path.** Not the directory's own basename (an earlier, superseded decision, D1): the basename alone collides in the real corpus (`workspace` is the basename of both a personal and an employer project directory, which would have merged their spend into one row). `resolveProjectSlug` (`src/parser/project.mjs`) reads the first `cwd`-bearing record from the first `.jsonl` in the directory via a **shallow, non-recursive** `readdirSync` — deliberately, because subagent transcripts live two levels deeper and their recorded `cwd` drifts into a worktree path a measured 27.5% of the time, which would poison the whole project's identity if one of those files were read first. The result is memoized per directory for the life of the process; only a real resolution is cached (a `null` "not found yet" is never cached), because a long-running backfill can revisit the same directory after more transcripts have landed, and a falsely-cached `null` would have been permanent under the old `$setOnInsert` rule.

- **`repoKey` is a hash of the normalized git remote, and the URL is never stored.** `src/parser/repo.mjs`'s `resolveRepoKey` runs `git remote get-url origin` in the recorded `cwd`, normalizes it (SSH and HTTPS forms of the same remote, trailing `.git`, trailing slash, and case all collapse to one canonical string), and stores only `sha256` of that string. This groups a worktree with its main checkout (both point at the same remote) without ever writing an employer/org-identifying URL into hosted Atlas — the same motivation that shrank `projectSlug` from a full path to two segments (D5) applies one level further here (D20). `repoKey` is optional by design (`undefined`, never a guessed value) whenever no repository resolves. Grouping worktrees with their main checkout was theoretical until per-turn attribution: with one slug per project directory, every repository in the real corpus had exactly one slug and the merge never fired. It now does — four worktree directories resolve to their main repository's key, which is what keeps the Repo tab distinct from the Project tab.

- **A wrong `CLAUDE_USAGE_API_URL` fails completely silently.** `postEvents` returns `{sent: 0}` on any non-2xx without throwing, and `syncTail` degrades every failure mode to a no-op by design — so a URL pointing at the wrong service produces no error, no log and no hook latency, indefinitely. Found the hard way: `http://localhost:3001` had been taken over by an unrelated Next app, every live hook sync had been 404ing into the void, and a backfill sent 2,375 requests before the summary line (`0 events, 2375 failures`) made it visible. The summary is the only place this surfaces at all; the hooks never will.

- **`{sent: 0}` has at least four meanings, and they are indistinguishable from the outside.** Nothing to send, wrong host, wrong secret, or a held lock all return the same value. Fixing the URL above exposed the next one underneath it: the sync still reported `{sent: 0}` because `/api/sync` was answering **401** — the local secret no longer matched the deployed one.

  **The probe that tells them apart** — POST an empty batch and read the status directly, rather than inferring it from `sent`:

  ```js
  const res = await fetch(resolveSyncUrl(process.env.CLAUDE_USAGE_API_URL), {
    method: "POST",
    headers: { "Content-Type": "application/json", "x-claude-usage-secret": process.env.CLAUDE_USAGE_SECRET },
    body: JSON.stringify({ machineId: "probe", events: [] }),
  });
  // 200 {"accepted":0,"rejected":0} = host and secret both good. 401 = secret. Anything else = host.
  ```

  An empty batch is safe: it writes nothing and still exercises auth and routing. Do this **before** concluding a sync works, and before spending ten minutes on a backfill.

- **`~/.claude/claude-usage` is a SYMLINK to the checkout, so there is only ONE `.env`.** `resolveDotEnvPath` prefers the installed path and falls back to the repo root, which reads as two files and was recorded as two for a while — they are the same inode. Editing either edits both, and "I fixed one of them" is not a thing that can happen.

- **The secret travels in `x-claude-usage-secret`, not `Authorization: Bearer`.** `SECRET_HEADER` is declared twice — `bin/sync.mjs` and `src/app/api/lib/verify-secret.ts` — and a probe using the conventional bearer header gets an indistinguishable `401`.

- **The deployed secret is a `random.RandomPassword` in Pulumi** — `pulumi stack output claudeUsageSecret --show-secrets` (the stack is org-qualified and already selected, so no `--stack` flag is needed; `PULUMI_ACCESS_TOKEN` must be exported first or the CLI hangs).

  This machine's `.env` held a *different* dev value until 2026-08-05, which is what made every sync 401 even after the URL was corrected. It now holds the deployed one, so hooks authenticate on their own. Two consequences: the local `npm run dev` login takes that same secret, and the e2e suite is untouched by any of it — `playwright.config.ts` overrides `CLAUDE_USAGE_SECRET` with `E2E_SECRET`, a throwaway that deliberately is not the deployed value.

  When writing it locally, pipe it straight from `pulumi stack output` into whatever rewrites the file. Passing it as an argument puts it in the process list; echoing it puts it in a terminal scrollback and, if an agent is driving, into a transcript.

- **A day is `Asia/Ho_Chi_Minh`, applied inside the aggregation** (`DASHBOARD_TIMEZONE` in `src/server/usage-queries.ts`, fed into Mongo's `$dateToString` `timezone` option — not computed client-side). Fixed, not derived from UTC or the viewer's browser zone: at UTC+7, midnight UTC is 07:00 local, so a UTC day boundary would misfile a full morning's work into "yesterday"; a browser-local boundary would make the same query return different totals depending on where it's opened. **Totals over a range containing unpriced events render as a lower bound** (D17) — e.g. `$412+ (18 events unpriced)` — because silently summing only the priced events reproduces the exact "reads as free" failure the `priced` flag exists to prevent, one level up in the aggregation.

- **The zero-dependency half is plain `.mjs`, no build step.** `src/parser/`, `bin/`, `hooks/`, `scripts/` (plus the local-only status line/report code) run directly under Node with no compile/bundle step — `README.md` states this explicitly ("Update with `git pull` — there is no build step"). This is why a `git pull` can never leave the status line or sync hooks broken by a stale build artifact: there's nothing to build. Only the dashboard (`src/app/`, `src/server/`, `src/components/`) is TypeScript/Next.js and has a build step. **There is no automated check across that boundary** — `src/parser/events.mjs`'s `MappedUsageEvent` typedef and `src/server/usage-store.ts`'s `UsageEventDocument` interface must be kept in sync by hand (the parser module is excluded from `tsconfig`, so nothing type-checks the two shapes against each other); a comment on each says so.

## How to work on it

- **Two independent test runners**, both must pass; neither substitutes for the other:
  - `npm run test:cli` (`node --test tests/*.test.mjs`) — covers the zero-dependency half: parser, hooks, install, backfill, sync.
  - `npm run test:server` (`vitest run`) — covers the Next.js half: API routes (tested by direct handler import against a real in-memory `mongodb-memory-server`, not a spawned dev server — D13), `usage-store`, `usage-queries`.
  - `npm test` runs both in sequence.
- **The hooks must never block or erase a prompt.** `UserPromptSubmit` exiting with code 2 erases the user's prompt outright — both hooks (`hooks/user-prompt-submit.mjs`, `hooks/session-start.mjs`) catch every failure path and always `process.exit(0)`. `UserPromptSubmit` additionally must return fast: it spawns `bin/sync.mjs` `detached: true` with `stdio: "ignore"` (not just `detached` — Claude Code captures the hook's own stdout/stderr as pipes, and a wait on an inherited pipe only reaches EOF once every process holding its write end closes it, including a "detached" grandchild that still inherited the pipe) and exits without awaiting the upload.
- **`shadcn add` reverts hand-edits to `globals.css`.** The shadcn CLI regenerates `src/app/globals.css` on every `init`/theme change; the current file is a pre-existing, out-of-scope-to-edit shadcn theme (chosen registry: `chart` component on Recharts). Do not hand-edit it expecting the edit to survive a future `shadcn add`.

## Known limitations — not yet proven in production

- **Not deployed.** This build ships code, tests, and a `personal-infra` PR that adds the database to provisioning — but no Vercel project exists yet and nothing has been deployed (D3, deliberate: the Vercel project needs credentials and a domain decision outside this run's scope).
- **Never run against real MongoDB Atlas or the real hosted API.** All measurements — including the ones below — were taken against `mongodb-memory-server` or a local throwaway HTTP server; no request in this codebase's history has hit a real Atlas cluster or a deployed `/api/sync` endpoint.
- **Backfill and the `SessionStart` full sweep *have* been exercised against the real transcript corpus** (201 real project directories, 2,222 real `.jsonl` files, 53,999 real events, zero cross-file `(requestId, messageId)` collisions), but only posting to a local throwaway server standing in for the real API — never against the real hosted endpoint end to end.
- **The installer (`scripts/install.mjs` / `src/install.mjs`) has never been run against this machine's real `~/.claude/settings.json`** — only against a faked `$HOME` in tests, by explicit instruction not to touch the real file during this run.
- **`SessionStart` now blocks ~1.4s inline on the largest real transcript on this machine** (261 MiB, measured 1,372 ms / 10,846 events / 6 batched requests, up from a 29 ms tail-only baseline) — acceptable relative to the 5 s client fetch timeout this codebase already tolerates elsewhere, but a real, honest latency regression on session start for that one session, not something to dismiss as noise. A typical session (4.6 MiB) is unaffected (~74 ms).
- **No staleness signal if sync silently stops.** Every failure mode in `bin/sync.mjs` (no network, non-2xx response, missing `.env`, missing/unreadable transcript) degrades to a silent no-op by design — there is no local watermark, no `lastSynced` field, and no dashboard surface showing when a machine last successfully synced. A machine can stop syncing entirely (bad secret, expired URL, `.env` deleted) and nothing anywhere will say so; this was confirmed absent by search, not assumed.

  No longer hypothetical: this machine ran from 2026-08-04 to 2026-08-05 sending nothing at all — first a dead host, then a stale secret — and the only symptom was a dashboard whose newest bar quietly stopped advancing. It was noticed because someone looked at the chart, which is exactly the detection mechanism this gap describes as missing. A "last successful sync per machine" figure on the dashboard would have caught both faults on day one.
- **`repoKey`'s unsalted hash is dictionary-reversible for a known or guessable repo name.** It is not invertible in general, but it is trivially *confirmable*: `sha256` over a short, low-entropy, guessable normalized string (`github.com/org/repo`) means anyone with collection access and a candidate repo name can confirm-or-deny that repo's presence at roughly 1M guesses/sec/core — proven by recovering a real repo's identity from its stored hash via a 4-candidate dictionary. This defeats casual browsing of Atlas (the actual concern D20 was chosen to address) but not a targeted guess against a named or enumerable repo.

## Contradictions found in the source material

- **`README.md` is stale relative to the shipped code.** It still states "Phase 2 (cross-machine sync) and Phase 3 (dashboard) are planned but not started" — both are in fact built, tested, and documented throughout `DECISIONS.md`/`IMPLEMENTATION_PROGRESS.md`. Left as-is per the instruction not to modify source files; worth a follow-up edit.
- **D1 ("project identity is the basename only") is superseded by D5 ("last two path segments")** within `DECISIONS.md` itself — not a live contradiction in the shipped code (which implements D5), but a reader skimming only D1 would land on the wrong rule. Noted here so it isn't mistaken for two competing live behaviors.
- **The task brief's framing of "backfill never run against the real corpus"** does not match `ADVERSARIAL_REVALIDATION.md`: backfill *was* run against the real 201-transcript, 2,222-file corpus (with success counts recorded), just never against the real hosted API/Atlas. The limitations section above states the more precise version rather than the brief's framing.
