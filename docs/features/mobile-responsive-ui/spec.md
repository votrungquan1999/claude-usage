# Mobile-responsive dashboard, and machine nicknames

A living spec for two things that shipped together because the second was blocked on the first: a dashboard that works on a phone, and a machine identified by an operator-assigned nickname instead of its 64-character hash.

The dashboard's reading surface has its own spec at [`../claude-usage-dashboard-insights/spec.md`](../claude-usage-dashboard-insights/spec.md), the drill-down pages at [`../split-drilldown/spec.md`](../split-drilldown/spec.md), and the sync write path at [`../claude-usage-sync-dashboard/spec.md`](../claude-usage-sync-dashboard/spec.md). Their invariants still hold and are not restated here, except where this feature adds to one — the nickname's own entry in the sync spec's privacy invariant is one such addition, made there rather than here.

## What the feature does

At 390×844 — an ordinary phone in portrait — the dashboard used to be 433px wide against the e2e test corpus and **749px wide against a real 64-character machine id**, both measured, not estimated. Every card scrolled sideways along with the page, charts squeezed to a sliver, the widest table had no keyboard route into it at all, and touch targets ran 28–32px. None of that is true anymore: at 390px the page requires no horizontal scrolling, charts keep a readable plot area with short axis ticks and a wrapping legend, every wide table scrolls inside its own region with a pinned identifying column, and every interactive control reaches at least 44px in its tappable dimension. Desktop is unchanged throughout — every sizing change is asserted at both viewports, not only the new one.

Underneath the layout work, a machine was identified on screen by its raw id — a 64-character hex hash that means nothing to the person reading it. It now carries an operator-assigned nickname instead, editable from the Machine sync tile, including from the phone that's reading it. Every surface that shows a machine — the sync tile, the session list, the split totals table, the chart legend and tooltip — shows the same name. This was the larger of the two changes: it is the app's first browser-driven write, and it touches a data model that previously had none.

## The root cause, and why it was one fix

`dashboard-shell.ui.tsx:55` read `<main className={cn("gap-6 p-8", "grid")}>`. A bare `grid` creates exactly one implicit column track, sized `auto` — and an `auto` track's *minimum* width is the largest min-content width among its children. Every one of `main`'s children was stretched to match whichever sibling was least willing to shrink, so one unshrinkable descendant set the width of the entire page. The same defect, byte-identical, existed at `split-value.ui.tsx:9` (the drill-down layout) and `session/[id]/page.tsx:32` (the session detail layout, a server component that had to gain a new `.ui.tsx` — `session-detail.ui.tsx` — before it could carry the fix, since ADR 0001 forbids styling in a server component).

The fix is the same in all three places: `grid grid-cols-[minmax(0,1fr)]`. `minmax(0, 1fr)` overrides the implicit track's `auto` minimum with an explicit `0`, so the track's width is set by the container, not by whichever child is widest — a wide descendant can now be asked to shrink (or scroll internally) instead of dragging every sibling wide with it.

Two descendants were actually driving the old width, and both mattered independently. The date-range row (`w-44` preset trigger + a `whitespace-nowrap` calendar label = 369px) was present on every dataset regardless of content. The raw machine id (+316px over its shortened form) only showed up once real data replaced the e2e fixtures' short, deliberately human-readable ids — which is exactly why Step 1 of this feature rewrote the e2e fixtures to 64-character hex before touching any layout: against the old 10–11 character fixture ids, a mobile-width test could pass while a real phone was still broken, and it would have passed for the entirely wrong reason.

## Load-bearing invariants

### The display name is a label, never a key

At `dimension-totals-table.ui.tsx` the colour lookup, the drill-down href and the visible row text all used to read the same `total.dimensionValue`. At `cost-chart.tsx` the same series `key` drove the legend/tooltip text and the colour slot. Once the Machine dimension could show something other than its own key, substituting the nickname into either of those positions would have broken colour stability (`assignSeriesColorSlots`) and the drill-down link in the same stroke. Both components stayed dimension-generic — they render project slugs, model names and repo labels through the identical code path — so the nickname substitution is gated to the Machine dimension only and only ever touches the text node, never the key either sibling reads from.

The drill-down URL is the sharpest edge of this. `/split/machine/<machineId>` carries the raw id, not the nickname (D12) — `splitValueMatch` resolves the Machine dimension by a raw `{ machineId: value }` equality, so a nickname in the URL would match no document and the row would link to "No data in this range" on a machine with obvious spend. That is not a hypothetical: it's the same label≠key failure class the split-drilldown spec already records happening twice on this dashboard's repository dimension, and the Machine dimension had only ever been immune to it because, until this feature, its label *was* its key. Addressing the drill-down by id rather than by nickname is what makes that whole failure class structurally impossible here rather than merely avoided by discipline — and it means a bookmark survives a rename, at the accepted cost that the 64-char hash still appears in the address bar and Machine now addresses differently from Project/Model/Repo.

### The label is applied after ranking, never before

`rankDimensionTotals` groups and sums by the label *string* it's given. Nicknames are not required to be unique (D16) — two machines can legitimately carry the same name — so if the display substitution ran before that ranking step, two same-named machines would silently merge into one row whose cost is the sum of both, while the grand total above the table kept tallying correctly and gave no sign anything had merged. The substitution runs strictly after ranking, at the render site only, so grouping, colour assignment and the href all continue to key on the raw machine id regardless of what any machine is named.

### The 20-bar chart cap holds at every viewport

`MAX_CHART_BARS = 20` did not change for mobile (D3). A phone gets the same bucketing as desktop for the same date range — shorter axis tick text (`26-07-06`, keeping two digits of year so a multi-year corpus never shows two ticks that read identically), `interval="preserveStartEnd"` plus a raised `minTickGap` so recharts' own pixel measurement thins ticks without hiding either end of the window — but never a different number of buckets. A viewport-aware cap would have made a phone and a desktop report different numbers for the identical query, which contradicts the dashboard-insights spec's own honesty rules about a chart's figures.

### 44px applies on mobile only, and desktop is asserted, not assumed

Every control that reaches 44px on a phone — the range preset, the calendar's day cells and nav buttons, the `Machine | Project | Model | Repo` tab strip, the session sort control, the pager — keeps its original desktop size (D4). 44px everywhere would make the desktop dashboard taller and less dense for no benefit on a device with a pointer, so every one of the six e2e tests covering this measures both viewports in the same test rather than asserting the mobile number and trusting desktop was untouched. The one control-height edit that needed real care was the primitive's own gated modifier syntax (`data-[size=...]`, `group-data-*`) — a plain `h-11` override loses to those in twMerge's cascade order, so every override repeats the exact modifier chain the primitive already uses.

### "Mobile" is a viewport predicate everywhere except the chart tooltip trigger

Every sizing and layout decision in this feature keys off Tailwind's breakpoints — a question about available space. The one exception is the chart tooltip's trigger, which keys off `window.matchMedia("(hover: hover)")` — a question about input capability, not space (D13/D21). This is the only JS media query anywhere in `src/`. It exists because recharts 3.8.0 makes hover and click trigger modes mutually exclusive on one static prop (traced through `combineTooltipInteractionState`), so a viewport-based choice literally cannot serve both a desktop mouse and a phone's tap at once the way every other sizing decision can. The accepted asymmetry: a touch-capable tablet at desktop width keeps hover, and a mouse-driven browser window narrowed to 390px gets sizing meant for touch. The query lives once, exported from `chart.tsx` as `useChartTooltipTrigger()`, and all five chart files call it identically rather than each running its own `matchMedia`.

### A failed nickname read falls back to short ids, and never blanks a card

`loadMachineSyncStatus` is `cache()`-wrapped, and `cache()` caches *thrown* errors, re-throwing them to every consumer. A shared nickname loader that threw on failure would give the sync tile, the session list, the split totals table and the chart legend — four previously independent cards, each with its own `CardErrorBoundary` — one common failure point, so a naming outage would cost the operator their actual spend figures along with it (D19). Every site that reads nicknames wraps the read in its own `try`/`catch`; on failure the machine renders under its short id and every dollar figure around it renders normally. This was proved, not just implemented: the `try` bodies in `cost-split-view.tsx` and `session-table.tsx` were temporarily replaced with an unconditional `throw`, and the totals table, the chart and the session list all kept rendering real figures with only the machine name degrading — reverted immediately after.

### The rename route authorises itself, because nothing else will

`src/proxy.ts:38`'s matcher is `["/((?!login|api|_next/static|_next/image|favicon.ico).*)"]` — `/api` is explicitly excluded, so the proxy's session check never runs on `POST /api/machines`. The route's own checks are the only authorisation that exists, and they run in a specific order so an unauthenticated or malformed request never touches the database: **401** (`verifySecret(request)` fails — no secret, or a wrong one) → **403** (the `Origin` header's host doesn't match this server's host, or is absent — `sameSite: "lax"` on the session cookie was never *chosen* as a CSRF control, it was inherited from the login cookie, so this three-line check is what turns that into a decision rather than a one-attribute accident) → **400** (the body doesn't parse, or `machineId`/`name` aren't usable strings, or the normalised name is too long or contains a disallowed character) → **404** (the machine id isn't in the roster). Two tests prove the ordering, not just the outcome: a request with a wrong secret and a corrupted `MONGODB_URI` still returns a clean 401, and a request with a valid secret/origin but an over-length name never reaches the roster lookup that would otherwise touch Mongo.

The nameable set — the roster — is the union of machine ids in `usage_events` and in `machine_sync_state` (`machineSyncStatus()`), not a bare existence check against `machine_sync_state` alone (D18, amending the plan's original D9 clause). `recordMachineSync` is deliberately skipped for backfills and empty batches, so a machine can have real spend, appear on the dashboard, and have no state document indefinitely — under a bare-existence check, exactly those machines (the ones whose identity is least obvious) could never be named. The roster check still does its actual job: an id absent from both sources is refused with no upsert, so a typo in a client can't conjure a phantom machine row.

### An empty name clears; the 40-character cap is what actually prevents a 64-hex name

Saving an empty or whitespace-only name clears the nickname rather than returning a 400 (D14) — a machine that could never be un-named again would give the operator no undo, and Step 10's own clearing requirement would otherwise directly contradict Step 9's "unusable name is a 400" rule. A name that is present but unusable — over the cap, or containing a control or bidi-override character — is what actually 400s. Names are trimmed and internal whitespace runs collapsed (`normalizeMachineName`) before either check runs, so `" Studio "` and `"Studio"` are the same stored name.

The cap is 40 characters (`MAX_MACHINE_NAME_LENGTH`, D29) — no repo precedent existed for this value; it was chosen deliberately below 64 because a human-readable name in a proportional font is not obviously narrower than a 64-character monospaced hash, and the cap's whole job is to stop a nickname from recreating the same overflow the hash itself caused. D15's stated rule was two checks — "cap the length, **and** reject a name that is 64 hex characters" — but once the cap sits below 64, any 64-character string, hex-shaped or not, already fails the length check first (D30). A standalone hex-format check would be dead code no black-box test could ever prove live, since nothing can trigger it without also triggering the length check first. So the length cap alone is what satisfies the actual property D15 cares about, and there is no separate hex-format regex anywhere in `route.ts`. If a materially larger cap is ever wanted, the hex check should come back as an independently meaningful rule at that point — noted at D30 rather than decided silently.

## Things a test cannot tell you here

The full suite is green: `npx tsc --noEmit` clean, 230 server tests, 132 CLI tests, and **54/54 e2e** across both the desktop and phone projects. That run is worth stating plainly because an earlier pass could not execute it at all (a macOS mach-port `bootstrap_check_in` failure stopped Chromium launching), and running it afterwards immediately caught a real failure the reasoning had missed: capping the pinned column's width narrowed the totals table, which shrank the available horizontal overflow below the fixed 15px threshold a test used to prove that scrolling had happened. That test now asks the scroll container for its own `scrollLeft` instead of assuming a pixel budget, so it survives any future width change.

That same run also surfaced an intermittent failure worth knowing about before writing the next chart test: three tap tests called `scrollIntoViewIfNeeded` on the chart *before* waiting for anything, and `ResponsiveContainer` swaps its SVG children once it has measured its own width — so a locator resolved before that point detaches, and the test dies with "Element is not attached to the DOM". It moved between tests from run to run, which is what made it read as flake rather than as a race. The fix was to delete the up-front scroll entirely: `tap()` already scrolls its target into view and retries on a detached element, so the explicit call bought nothing and only opened a window in which the DOM could be touched too early.

The chart legend-wrap test asserts only the CSS property (`flex-wrap` present) rather than a real multi-row overflow. The fixture corpus has exactly two machines on the Machine tab, and their ids are short, unspaced 8-character hex strings that cannot soft-wrap internally the way a longer name could — so a genuine multi-row legend can't be produced without changing fixture conventions outside this feature's scope. The test will keep passing exactly as written the day a fifth or sixth machine's legend entry actually needs to wrap; it just can't prove that day works yet.

The four risks that were once reasoned about but unverified have since been checked in a live browser, and the results are worth keeping. The repoKey-leak assertion genuinely fires: rendering a real 64-hex repoKey outside the table makes `drilldown.spec.ts` fail, which it did not do before this feature (the fixture's own `REPO_KEY` was 63 characters, so the guard could never match anything). The `sm` boundary behaves exactly as D21 accepted — 44px controls at 639px, today's 32px at 640px and above, and no horizontal overflow at 639/640/767/768. The range calendar in landscape is usable: it shows two months and extends past a 390px-tall viewport, but paging back works and every day cell is reachable by ordinary vertical scrolling, with no horizontal overflow.

The fourth is the one that mattered. The pointer-capability trigger (D13) had three passing tests and **none of them could tell whether it worked**: forcing `useChartTooltipTrigger` to return a constant left all three green, because Chromium synthesises mouse events from a tap, so a tap opens the tooltip in either mode. The mode is now reflected on the chart container as `data-tooltip-trigger` and asserted directly, and that assertion does fail when the hook is neutered. If you change how the trigger is chosen, that is the test that will notice.

Two machines whose ids happen to share their first 8 characters render byte-identical short ids everywhere on screen — the tile, the totals table, the chart legend, the session list. The only disambiguating signal is the full id in an `sr-only` span and a `title` attribute, neither of which helps on a touch screen, the primary device class this feature was built for. The one real defence against this is naming either machine — once a nickname exists, `machineDisplayName` never falls back to the shortened id for it. Nothing detects or warns about the collision itself; it's silent until an operator happens to notice two rows that look the same.

A machine's id changing — a Claude Code reinstall mints a new one — has no decision recorded anywhere and no handling in the code. The new id shows up unnamed; the old id's nickname sits on a roster row that will never sync again. Nothing merges them, nothing warns that they might be the same physical machine, and nothing retires a machine at all — general retirement (an operator deciding a machine is gone for good) is unbuilt as a concept, not deferred as a specific mechanism. The only available workaround is manually renaming the new id to match the old machine's name, which nicknames' lack of a uniqueness requirement (D16) happens to allow.

Zero-width characters used to survive nickname validation, which meant `"Studio"` and `"Studio" + U+200B` stored as different names that rendered identically. They are now stripped during normalisation rather than rejected, matching how that function already treats stray whitespace — the operator meant the visible text, and a name made only of them normalises to empty, which D14 reads as clearing the nickname. ZWNJ (`U+200C`) and ZWJ (`U+200D`) are deliberately left alone: both carry real orthographic meaning in Persian and Indic scripts and are what join emoji sequences, so stripping them would corrupt a name typed on purpose.
